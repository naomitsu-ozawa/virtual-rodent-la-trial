# マウス後足 microCT データセット（関節炎モデル、Virtual Rodent Lab 用）

Virtual Rodent Lab（以下 VRL）でそのまま読み込める形に変換した、関節炎モデルマウス後足
microCT の DICOM 一式とプロジェクトファイルです。正常個体 889 のデータセット
（`hindpaw_889_2m`）と対になる、同じコホート・同じ撮像プロトコルの関節炎モデル個体です。
リポジトリ自体には一切手を入れていません（読み取りのみで仕様を確認し、成果物はこのフォルダに置いています）。

## 中身

| パス | 内容 |
|---|---|
| `dicom_ct/` | CT の DICOM シリーズ（340 ファイル、`HindpawCT_0001.dcm` 〜 `HindpawCT_0340.dcm`、約 68 MB、値は HU） |
| `dicom_labels/` | 骨ラベルの DICOM シリーズ（340 ファイル、`HindpawLabels_0001.dcm` 〜、約 68 MB）。CT と同一グリッド |
| `hindpaw_154_2m_arthritis.vrlab` | VRL プロジェクトファイル（CT シリーズに紐付き、骨セグメント定義＋骨ラベル由来の解析領域 33 件・骨名ピン付き） |
| `screenshot_154_vrl.png` | VRL 実画面でプロジェクトを適用し、解析ドックに領域一覧が表示された状態のスクリーンショット |

## VRL での使い方

1. VRL で `dicom_ct` フォルダの DICOM を読み込む（CT シリーズが自動選択される）。
2. プロジェクトファイル `hindpaw_154_2m_arthritis.vrlab` を読み込むと、表示ウィンドウ（中心 1000 / 幅 4000）と
   骨セグメント（HU 1200〜7065、色 `#f3f0e8`、有効化済み）、骨名つき解析領域 33 件が適用される。
3. `dicom_labels` は別シリーズとして読み込める（値は 889 データセットと同じラベル番号体系）。
   CT と ImagePositionPatient グリッドが完全一致するので、外部ツールでもボクセル単位で対応づけられる。

## 元データの実測結果（変換前の検査）

- CT（`154-2m.modif`、1,811,052,707 bytes): AmiraMesh BINARY-LITTLE-ENDIAN 3.0、
  格子 1364（x）× 892（y）× 372（z)、float32。BoundingBox x 11.3447399〜35.0608025 /
  y 10.1615400〜25.6648502 / z 60.6660004〜67.1205978 mm から、間隔は
  **x・y = 0.0173999 mm、z = 0.0173978 mm**(889 の元 DICOM と同一プロトコル）。
- **CT 値は HU**: Amira が元 DICOM の格納値に RescaleSlope 0.391063 / RescaleIntercept −1000 を
  適用した値で書き出している（値域 −2236〜6917、骨ラベル内は最小 1201・中央値 3834)。
  889 の "Processed Data"（骨だけの 8-bit 処理値）とは異なり、本データは軟部組織を含む通常の CT である。
  本変換では HU のまま 16-bit 符号付き DICOM に格納した（Rescale 0/1)。
- ラベル（`154-2m.grown`、8,519,835 bytes): 同じ格子の byte ボリューム、**HxByteRLE** 圧縮。
  デコード方式（制御バイト <128 は繰り返し、>=128 はリテラル列）は、デコード総数
  452,607,936 が格子総数と完全一致し、値が 0〜66 の 67 種・非ゼロ 6,023,704 ボクセルで
  Materials 定義と整合することで実証した。
- Materials は 67 件（0=Exterior + 骨 66 件）で、**両足分**の骨が材料名（DP4R、MET5L 等、
  末尾 L/R が足の区別）で入っている。1 足あたり 32 材料（末節骨 4・基節骨 5・中足骨 5・
  種子骨 10・足根骨 6・FIBTIB・TIB）＋両足共有の CLAW（爪）・FLOAT（過剰種子骨）。
  889 との違い: 脚は TIB（脛骨単独）と FIBTIB（脛骨・腓骨）の 2 材料に分かれている。
- 視野内には後足が 2 本写っている。本変換の対象は、889 のクロップと位置的に対応する
  **高 y 側の足**(L 材料群）である。ただし 154 は両足が近接する姿勢で、矩形クロップの
  範囲内に反対足の前足部の一部（元解像度で約 50 万ボクセル分の骨）が写り込む。
  CT にはそのまま残してあるが、ラベルと解析領域は対象の足のみである。

## 変換内容（何をどう変えたか）

889 の変換と同じ手順・同じ規約を適用した。画素値の加工はクロップとダウンサンプル以外していない。

1. **ラベルの番号付け替え**: 材料名（例: DP4L）を、889 データセットのラベル番号体系に
   対応付けた（対応表は次節）。TIBL + FIBTIBL は合体して 889 のラベル 48 (FIBTIB）とした
   （889 では脛骨・腓骨が 1 材料）。CLAW と FLOAT は両足にまたがる材料のため連結成分に分け、
   対象足側の成分だけを採用した（CLAW は対象足の末節骨・基節骨に隣接する 5 成分＋微小片 3 個、
   FLOAT は第 5 中足骨への最近傍距離 9.8 ボクセル（反対足側は 286.7）で対象足側と確定した成分）。
2. **クロップ**（元ボクセル座標）: x 183〜1184、y 380〜773、z 32〜371。
   889 のクロップ余白（足の bbox に対して x0 −24 / x1 +49 / y0 −32 / y1 +25 / z0 −36 / z1 は終端）を
   本個体の対象足 bbox にそのまま適用し、面内寸法が偶数になるよう調整した。
3. **面内ダウンサンプル ×1/2**: CT は 2×2 面積平均（四捨五入）、ラベルは 2×2 多数決
   （同数時は非ゼロ優先→小さい値）— 889 と同じ規則。画素間隔 0.0173999 → 0.0347998 mm、
   スライス間隔は元のまま 0.0173978 mm。結果: **501 列 × 197 行 × 340 スライス**、実寸 17.43 × 6.86 × 5.91 mm。
   面内最大 501 < 512 のため、VRL の GPU 表示でも縮小されない。展開サイズは 1 シリーズ約 64 MiB で
   256 MiB のメモリ内処理条件に収まる。
4. **タグ**: 新 SeriesInstanceUID を生成、StudyInstanceUID は元ヘッダの値を保持
   (`2.16.756.5.23.5022.67.15485.1111`)。ImagePositionPatient は新グリッドで再計算（2×2 ブロック中心）。
   CT は PixelRepresentation 1（符号付き 16-bit)、Window Center 1000 / Width 4000。
   ラベルは符号なし 16-bit。両シリーズとも DerivationDescription に変換内容を英語で記録。
   転送構文は Explicit VR Little Endian・非圧縮、1 スライス 1 ファイル、Part 10 形式。

## プロジェクトファイルの中身

- 形式・構造は 889 の最終プロジェクトと同一（ZIP + `project.json`、
  `format: "virtual-rodent-lab-project"`, `version: 1`)。解析領域 33 件は全て bone セグメント所属、
  色はアプリの 14 色パレットをラベル昇順に循環、色・体積は次表のとおり。
- 骨セグメント: 範囲 **HU 1200〜7065** で有効化。根拠は実測: 出力 CT 上でラベル済み骨ボクセルの
  最小値は 1201 で、全ラベルボクセルが範囲内に入る。本データは軟部組織を含む通常の CT で、
  閾値だけでは骨と軟部組織を完全には分離できないため、セグメントはラベル（解析領域）の
  近似として扱い、正確な骨の範囲は解析領域側を正とすること。反対足の骨も閾値内に入るため
  セグメント表示には写る（ラベル・領域は対象足のみ）。
- ピン（解析領域の `label`）: 全 33 領域に骨名ピン付き。アンカーは各領域の最大成分の
  重心に最も近い表面ボクセル（出力グリッド座標）。889 の最終ファイルではアプリ内操作で
  表面アンカーが置かれたが、本データでは同じ保存形式で計算により配置した。
- 表示: windowCenter "1000" / windowWidth "4000"、ctRangeMode "auto"、
  初期スライス axial 170 / coronal 98 / sagittal 250。フィルタなし、3D 編集なし。

## 検証結果（すべて実測、アプリ自身のコードで実施）

- **DICOM 往復**: 書き出した CT 340 枚・ラベル 340 枚を読み戻し、変換元ボリュームと
  全ボクセル一致を確認。SeriesInstanceUID / StudyInstanceUID はプロジェクトと一致、
  ImagePositionPatient は z 単調増加（間隔 0.0173978 mm)。
- **プロジェクト**: `unpackProject` で正常に開け (project.json + 領域バイナリ 33 件）、
  `compareFingerprints` は ok、`resolveProjectMatch` は **apply**。
- **解析領域**: `decodeRuns` で全 33 領域を復号し、ラベルボリュームと集合比較:
  **全領域でボクセル集合が完全一致、領域同士の重なり 0、合計 818,376 ボクセル**。
  全領域でピンアンカーが領域内の表面ボクセルにあること、名称が対応表どおりであることも確認。
- **実画面**: `screenshot_154_vrl.png`（プロジェクト適用後の解析ドック表示）。

## 注記・未確定事項

- 間隔は AmiraMesh の BoundingBox 由来（元 DICOM が手元に無いため、889 のような
  DICOM タグ実測ではない）。x・y・z の値は上記のとおり実測値として記録している。
- 対象足を「高 y 側」としたのは 889 のクロップ位置との対応による。材料名の L/R 接尾辞は
  原典の命名だが、解剖学的な左右の確定情報は原典に無いため、名称・説明に左右は含めていない。
- FLOAT の対象足側成分は第 5 中足骨から約 10 ボクセル離れており、接触ではなく
  最近傍距離（対象足 9.8 vs 反対足 286.7 ボクセル）の圧倒的差で帰属を決めた。
- CLAW の対象足成分のうち 3 個は 1 ボクセルだけの微小片で、隣接規則で対象足側に
  含めた（合計 3 ボクセル、領域の体積への影響は無視できる範囲）。
