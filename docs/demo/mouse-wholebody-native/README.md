# マウス全身 microCT データセット（Virtual Rodent Lab 体験版用）

Virtual Rodent Lab — 体験版（`naomitsu-ozawa/virtual-rodent-la-trial`、以下 VRL）で
そのまま読み込める形に変換した、マウス全身 microCT の DICOM 一式とプロジェクトファイルです。
前回のマウス後足データセット（`hindpaw_889_2m`）と同じ形式・同じ手順で作成しました。
リポジトリ自体には一切手を入れていません（読み取りのみで仕様を確認し、成果物はこのフォルダに置いています）。

## 中身

| パス | 内容 |
|---|---|
| `dicom_ct/` | 全身 CT の DICOM シリーズ（200 ファイル、`WholeBodyCT_0001.dcm` 〜 `WholeBodyCT_0200.dcm`、約 4.8 MB） |
| `dicom_labels/` | 臓器ラベルの DICOM シリーズ（200 ファイル、`WholeBodyLabels_0001.dcm` 〜、約 2.5 MB）。CT と同一グリッド |
| `wholebody_m01.vrlab` | VRL プロジェクトファイル（CT シリーズに紐付き、元データの臓器セグメンテーションをセグメントのマスクとして登録：骨・肺・造影（臓器）の 3 セグメント＋子セグメント 10 件） |
| `sample.json` | VRL 練習データ形式のメタ情報（出典・ライセンス・変更点）。アプリ自身の `parseSample` で検証済み（エラー 0） |
| `screenshot_vrl.png` | VRL 実画面（3D 表示、子セグメントの色分け＋セグメントツリー）のスクリーンショット |
| `screenshot_vrl_3d.png` | 同上（3D 表示、背側〜斜め上）のスクリーンショット |

## VRL での使い方

1. VRL で `dicom_ct` フォルダの DICOM を読み込む（CT シリーズが自動選択される）。
2. プロジェクトファイル `wholebody_m01.vrlab` を読み込むと、表示ウィンドウ（中心 100 / 幅 1200）と
   セグメント（骨・肺・造影＝臓器）が適用され、元データのセグメンテーションそのままの色分けで表示される。
3. `dicom_labels` は別シリーズとして読み込める（値 0〜11 が臓器クラス）。
   CT と ImagePositionPatient グリッドが完全一致するので、外部ツールでもボクセル単位で対応づけられる。

## 選んだスキャンと根拠

zip 内には 141 スキャン分（M01〜M20 × 時点 0.25 h〜72 h、ネイティブ系列）のフォルダが入っている。
本変換では **M01 の 0.25 h**（個体 M01、投与後 0.25 時間＝この系列の最初の時点）を選んだ。根拠:

- 論文 Figure 1 でネイティブ例として使われているのが #M01-0.25 h である。
- この時点には独立した手動セグメンテーションが 2 件（Organ1 / Organ2）付いており、相互比較で品質を評価できる。
- 臓器ラベル付きの代表 1 件という用途では、最も早い時点が「ベースライン」として扱いやすい。

各フォルダの中身は NIfTI ではなく **Analyze 7.5 形式**（`.hdr`/`.img` ペア）だった
（CT140 = 0.14 mm グリッド、CT280 = 0.28 mm グリッド、Organ1 / Organ2 = 臓器セグメンテーション、
Bed = 寝台・全身・fiducial のセグメンテーション、各々に `.cls` のクラス定義ファイル付き）。

- 使用したのは **CT280**（142 列 × 105 行 × 200 スライス、0.28 mm 等方）。臓器セグメンテーションが
  このグリッド上で作られているため、ラベルのリサンプリングが一切不要になる。
  CT140（284×210×400、0.14 mm）から作る CT280 は元々「8 近傍ボクセルの平均」と論文に明記されており、
  配布 CT280 を使うことと等価である。
- セグメンテーションは **Organ2** を採用した。理由は「セグメント登録」の節を参照。

## 元データの実測結果（変換前の検査）

- CT280 の格納値は int16 で **−1000〜4513**。論文は「全ボクセルの強度は Hounsfield unit で校正
  （空気 −1000、水 0）」と明記しており、実測最小値もちょうど −1000 だった。
  **したがって格納値は HU である**（後足データと違い、今回は HU と称してよい）。
  ただし前臨床 µCT の校正であり、臓器ラベル内 HU の中央値は心臓 102、肝臓 147、腎臓 119 など
  臨床 CT の軟部値より高めに出ている（元データのまま、換算はしていない）。
- 寝台（Bed）のクラス 1 がマウス全身を指すことを確認した（Organ2 のラベル済みボクセル 235,216 / 235,611 が内包される。
  残り 395 ボクセルは Organ2 側が全身クラスの外側にはみ出して描いた分）。
- 臓器ラベルの z 範囲は頭頸部（気管 z 171〜199）から骨盤（膀胱 z 21〜39）まで全身に分布し、
  ラベル実測の解剖学的な並び（尾側→頭側: 膀胱・大腿筋 → 腸 → 腎臓 → 脾臓・胃・肝臓 → 心臓・肺 → 気管）も妥当だった。

## 変換内容（何をどう変えたか）

1. **クロップ**（元ボクセル座標）: 全身マスク（Bed クラス 1 ∪ 臓器ラベル）の bbox
   x 12〜128 / y 22〜97 / z 0〜199 に 5 ボクセルの余白を追加し、
   x 7〜133、y 17〜102、z 0〜199（z はラベルが両端まで届くため全域）とした。
2. **ダウンサンプルなし（倍率 1）**: クロップ後は **127 列 × 86 行 × 200 スライス** で、
   全軸とも上限 512 ボクセルを大きく下回るため、等方ダウンサンプルは不要だった（間隔は元の 0.28 mm のまま）。
   展開サイズは 127×86×200×2 byte = **4,368,800 bytes（約 4.17 MiB）** で、
   VRL のメモリ内処理の上限 256 MiB を大きく下回る。
   実寸は 35.56 × 24.08 × 56.00 mm。
3. **タグの付け替え**（シリーズとして成立させるため。前回の後足変換と同一規約）:
   - 新 Study / Series Instance UID（2.25.* 形式で生成）。元データ（Analyze 形式）には DICOM UID も
     撮像日も無いため、日付タグは変換日になっている。この点は各ファイルの DerivationDescription にも明記した。
   - CT シリーズ: SOP Class は CT Image Storage、Modality `CT`、ImageType `DERIVED\SECONDARY\AXIAL`。
     BitsAllocated / BitsStored 16、**PixelRepresentation 1（符号付き）** で HU の負値をそのまま保持。
     Rescale Slope 1 / Intercept 0。Window Center 100 / Width 1200（全身マスク内ボクセルの
     パーセンタイル — 中央値 117、99% 点 1566 — から設定した一般表示用ウィンドウ）。
   - ラベルシリーズ: Secondary Capture / Modality `SC`、ConversionType `WSD`、8-bit。
   - InstanceNumber は 1 始まり。ImagePositionPatient は新グリッドで再計算（原点 = クロップ始点×0.28 mm）。
   - 各ファイルに DerivationDescription (0008,2111) として変換内容を英語で記録。
   - 転送構文は Explicit VR Little Endian・非圧縮、1 スライス 1 ファイル、Part 10 形式。

## プロジェクトファイルの中身

- 形式: ZIP + `project.json`（`format: "virtual-rodent-lab-project"`, `version: 1`、拡張子 `.vrlab`)。
  構造はアプリのプロジェクトファイルの仕様に準拠。
- `dataset` フィンガープリントは、変換後 DICOM をアプリ自身のシリーズ判定に通して得た値そのもの
  （seriesUid `2.25.142013309489684951365364591977574378950`、127×86×200、spacing [0.28, 0.28, 0.28]）。
- 最終ファイルは、起動中の VRL アプリの中でセグメント編集マスク（keep）をアプリの状態に登録し、
  アプリ自身の保存機能で書き出したものである
  （savedAt はファイルに記録されている）。外部スクリプトで JSON を直接組み立てたファイルではない。
- 表示は windowCenter "100" / windowWidth "1200"、ctRangeMode "auto"、初期スライス axial 100 / coronal 43 / sagittal 63。
  `spacingCheck` はアプリの間隔チェック結果（警告なし）を記録。

## セグメント登録（元セグメンテーションをそのまま使う方式）

元データの手動セグメンテーション（Organ2）を、HU 閾値による近似ではなく **そのままのマスク** として
VRL のセグメントに登録した。仕組みは次のとおり:

- VRL のセグメントは「閾値範囲 ∩ 3D 編集マスク（keep）」で最終ボクセルが決まる
  （表面側と GPU ボリューム側）。そこで
  **閾値範囲をデータ全域（−1000〜4513）にし、keep マスクに臓器ラベルそのもの** を入れた。
  これによりセグメントの表示ボクセルはラベルマスクと正確に一致し、閾値法では避けられない
  体外の空気や撮影ベッドへの誤着色が原理的に起きない。
- プロジェクト zip 内には `edits/bone-keep.bin` / `edits/lung-keep.bin` / `edits/contrast-keep.bin`
  （アプリ自身の `encodeRuns` 形式）が格納されている。

| セグメント | 登録したラベル（Organ2） | ボクセル数 | 体積 (mm³) | 色（プリセット既定色） |
|---|---|---:|---:|:--|
| 骨 (bone) | クラス 1 Bone | 25,290 | 555.17 | `#f3f0e8` |
| 肺 (lung) | クラス 2 Lung ＋ クラス 3 Trachea | 10,620 | 233.13 | `#6fb8d6` |
| 造影 (contrast) | クラス 4〜11 の臓器すべて（下表） | 199,701 | 4,384.03 | `#c026d3` |
| 軟部組織 (soft) | — （無効） | — | — | — |
| 脂肪 (fat) | — （無効） | — | — | — |
| 合計 | | 235,611 | 5,172.21 | |

- **気管は気道として肺セグメントに含めた**（クラス 3 Trachea、257 ボクセル）。肺と連続する
  気道であり、表示上も 1 つの呼吸器系として扱う方が分かりやすいためである。
- **臓器（クラス 4〜11）は造影セグメントに合体して登録した**（ユーザーの指定による）。
  内訳は 心臓 8,721 / 膀胱 2,138 / 腎臓 11,110 / 胃 7,710 / 筋肉 765 / 脾臓 1,542 / 肝臓 62,317 / 腸 105,398 ボクセル。
  臓器ごとの個別表示が必要な場合は `dicom_labels` シリーズ（値 0〜11）側で参照できる。
- **解析領域は使っていない**（当初は臓器ラベルを解析領域として登録していたが、ユーザーの指示で
  「領域ではなくセグメントで登録」に改めた。ピン留めラベルも置いていない）。
- ラベル値→臓器名の対応は、推測ではなく同梱資料で確定している。各スキャンフォルダ内の
  `Organ2.cls`（Imalytics のクラス定義ファイル）が `ClassIndices` と `ClassNames` を明記しており、
  論文も「フォルダには .CLS ファイルが含まれ、クラス番号と臓器の対応を記述する」と説明している。
- **Organ1 と Organ2 の違い**: このスキャンには観察者 2 名分のセグメンテーションが付く。
  Organ2 を採用した理由は (1) **気管（Trachea）を含む 12 クラス**で臓器が 1 つ多い、
  (2) 骨マスクと高 HU ボクセルの整合が良い（HU ≥ 400 に対する precision: Organ2 0.91 に対し Organ1 0.37。
  Organ1 の骨は 89,369 ボクセルと Organ2 の 25,290 の 3.5 倍あり、低 HU 側まで広く取り込んでいる）。
  参考として、共有臓器での観察者間 Dice は 心臓 0.898、膀胱 0.889、腎臓 0.878、胃 0.841、肝臓 0.833、
  肺 0.813、腸 0.731、筋肉 0.500、骨 0.437、脾臓 0.328 だった（論文の Technical Validation が
  観察者間再現性の評価のために 2 件付けたもので、どちらが「正解」という位置づけではない）。
- **左右の扱い**: 元のクラス定義では肺も腎臓も左右別ではなく 1 クラス（Lung / Kidneys）である。
  そのため分割はしていない（資料で確定しない分割はしない）。
- 筋肉（Muscle）は論文の列挙では “thigh muscle”（大腿筋）に当たる。CLS の表記どおり「筋肉」とした
  （体積 765 ボクセルと小さく、大腿部の一部分のみが描かれている）。
- 1 ボクセル = 0.28³ = 0.021952 mm³ で換算。全セグメントの合計 235,611 ボクセルは
  ラベル付きボクセル総数と一致する。

### なぜ閾値セグメントではダメだったか（実測の記録）

当初は HU 閾値でセグメントを構成したが、ユーザーの指摘（「空気まで色ついてる」）を受けて実測したところ:

- 肺の閾値帯（−1000〜−300）には、空気そのものが −1000 HU のため **体外空気ボクセルの 99.99%** が入ってしまう。
  論文の肺セグメンテーションはシード点からの領域成長であり、閾値だけでは空気と肺は分離できない。
- 軟部の閾値帯（−100〜350）には、マウスベッド／カセットのプラスチック（中央値 +68 HU）が **85.4%** 入り、
  ベッドが巨大な板として着色された。
- 肺の下限を −700 に上げてもベッド表面の部分容積層（中央値約 −495 HU）が残り、閾値の調整では解消しなかった。

このため閾値方式をやめ、上記の「元セグメンテーションをマスクとして登録」方式に切り替えた。

## 検証結果（すべて実測）

アプリ自身のコード（アプリのコードを Node で実行）による検証:

- **CT シリーズ**: 200 スライスを 1 シリーズとして認識。Modality CT、127 列 × 86 行、
  spacing 0.28 × 0.28 × 0.28 mm、compact（Int16）true、sourceBacked false、展開 4,368,800 bytes。
  値域は元データ実測で −1000〜4513 HU（シリーズ情報の min/max は符号付き既定表示のため、
  画素実測値をここに記す）。
- **ラベルシリーズ**: 同一形状・同一 spacing、値域 0〜11。
- **spacingCheck**: 両シリーズとも `warn: false`、重複 0・欠落 0・ばらつき 2.5e-12 %、タグ間隔との不一致なし。
- **プロジェクト（最終・アプリ保存版）**: アプリで正常に開け、zip 内エントリは
  project.json + `edits/` の keep バイナリ 3 件 + `treesegments/` の子セグメントバイナリ 10 件
  （解析領域バイナリは無い）。
  指紋照合は ok、適用判定は **apply**。
- **子セグメント（追加）**: 保存ファイルをアプリに読み戻し、ツリーに
  子 10 件が表示されること、各子のボクセル数がラベル実測と一致すること（上表）、子同士が互いに素で
  全て親 keep の部分集合であること、親の表示ボクセルが 造影 0 / 肺 0 / 骨 25,290
  （keep − 子の合体）であることをアプリ内で実測した。
- **セグメントのボクセル照合**: 保存された keep バイナリをアプリ自身の `decodeRuns` で復号し、
  ラベルボリューム（`dicom_labels` 全 200 枚と画素単位で一致することを変換時に確認済みの作業ボリューム）と
  集合として比較: **骨 = 25,290 / 肺（+気管）= 10,620 / 造影（臓器合体）= 199,701 ボクセルで、
  3 セグメントともラベルマスクと集合が完全一致（不一致 0）**。ラベル同士は互いに素なため、
  セグメント間の優先順位による差し引きも発生しない。
